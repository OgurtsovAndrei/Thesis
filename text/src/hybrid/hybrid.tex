Chapter~\ref{chap:distributions} identified three distribution types.
Sequential and near-sequential keys have small local spread, so exact mode
(Section~\ref{sec:adaptive}) applies directly --- FPR~$= 0$ with no hash needed.
When keys are uniform over a large span, truncation
(Section~\ref{sec:truncation}) is effective: large inter-key gaps mean few phantom
collisions and low FPR.

Clustered keys (OSM, geospatial IDs) fit neither case alone: dense regions inside each
cluster behave like near-sequential data, while the sparse gaps between clusters have
large inter-key distances where truncation works well.

The hybrid idea is to split along this structure --- isolate each dense region into its
own exact-mode sub-filter (FPR~$= 0$), and route the sparse keys between clusters to
a fallback filter.

This chapter describes Seg-ARE, our segmentation algorithm based on 1D DBSCAN.


\section{1D DBSCAN in $O(n)$}
\label{sec:dbscan-1d}

DBSCAN~\citep{ester1996dbscan} is a density-based clustering algorithm.
It takes two parameters: a neighbourhood width~$\delta$ and a density threshold
\texttt{minPts}. A point is a \emph{core point} if it has at least \texttt{minPts}
neighbours within a window of width~$\delta$; a \emph{border point} if it is within
$\delta$ of a core point but not itself dense; and \emph{noise} otherwise. Clusters
grow from core points by absorbing all density-reachable neighbours.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.85\textwidth]{dbscan_1d}
    \caption{1D DBSCAN on a key sequence (minPts~$= 5$). Blue = core points (window
    contains $\geq$ minPts neighbours). Orange = border (within $\delta$ of a core,
        but $<$ minPts in own window). Gray = noise.}
    \label{fig:dbscan-1d}
\end{figure}

On a finite point set in a general metric space, the naive DBSCAN scan computes the
$\delta$-neighbourhood of each point in $O(n^2)$ time~\citep{ester1996dbscan}; the
original paper recovers $O(n \log n)$ with a spatial index such as an R-tree.
On sorted one-dimensional data, density queries reduce to a sliding window, giving an
$O(n)$ implementation without any auxiliary index.


\section{Seg-ARE: Design and Algorithm}
\label{sec:hybrid-scan}

\paragraph{Border expansion increases bits per key.}
Standard DBSCAN absorbs border points --- points within $\delta$ of a core but not
themselves dense --- into the nearest cluster.
This widens the cluster's span without adding proportional density.
The exact-mode ERE sub-filter encodes keys relative to that universe, so a wider span
means more bits per key.
Seg-ARE drops border expansion: the dense core alone minimises span and keeps the
sub-filter cost low.

\paragraph{Expressing $\delta$ through \texttt{minPts}.}
Standard DBSCAN treats $\delta$ and \texttt{minPts} as independent.
We choose $\delta$ small enough that every range produced by the forward sweep
fits the exact-mode budget of the underlying ERE sub-filter
(see Section~\ref{subsec:fpr-guarantee} for the derivation):

\begin{equation}
    \delta = \texttt{minPts} \cdot \frac{\mathcal{L}}{2\varepsilon} = \frac{256\,\mathcal{L}}{\varepsilon}.
    \label{eq:delta}
\end{equation}

This ties $\delta$ to \texttt{minPts}, leaving a single free parameter.

\paragraph{Choosing \texttt{minPts} = 512.}
The choice balances three concerns:
\begin{itemize}
    \item \textbf{Overhead per key.} Each segment costs roughly 700~bits of fixed metadata
    (\texttt{minKey}, \texttt{maxKey}, pointer, sub-filter header).
    At 512~keys this adds $\sim 1.4$~BPK; for smaller clusters the overhead quickly
    dominates the budget.
    \item \textbf{Query cost.} The segment count is at most $\lfloor n/\texttt{minPts} \rfloor$,
    so the binary search over segment boundaries (Section~\ref{subsec:query}) stays fast
    regardless of dataset size.
    \item \textbf{Detection power.} If \texttt{minPts} is set too high, genuinely dense
    sub-ranges with fewer keys go entirely to the fallback, negating the benefit of
    segmentation.
\end{itemize}
512 balances these concerns: small enough to catch real clusters, large enough to
keep per-segment overhead acceptable.

To sanity-check the scale: for $\mathcal{L} = 128$, $\varepsilon = 10^{-3}$ we get
$\delta \approx 3.3 \times 10^{7}$. Comparing this against the SOSD gap statistics
(Table~\ref{tab:sosd-gaps}), Facebook/Wiki/Books have median gaps well below~$\delta$
so most keys fall into segments, while OSM's median gap of $4.5 \times 10^{7}$ sits
right at the threshold --- segmentation captures only the denser sub-clusters.
A uniform 64-bit distribution has average gap ${\sim}2^{44} \gg \delta$, so every key
goes to the fallback and Seg-ARE degrades to plain truncation.

\subsection{Algorithm}

Seg-ARE runs in three steps:

\begin{enumerate}
    \item \textbf{Forward sweep:} slide a two-pointer window. Whenever the window holds
    $\geq \texttt{minPts}$ keys, record the index range $[\textit{left}, \textit{right}]$.
    \item \textbf{Conditional merge:} adjacent ranges with key-space gap $\leq \delta$ are
    joined only if the combined span is below $m'\mathcal{L}/\varepsilon$,
    where $m'$ is the total key count of the merged segment. Otherwise they remain separate.
    \item \textbf{Fallback:} all keys outside merged ranges go to the fallback filter.
\end{enumerate}

\subsection{Fallback}

Keys not assigned to any segment go to a single fallback ARE filter.
Depending on the density of the fallback keys, this may be a truncation filter
or a hash-based one.

\subsection{Query}\label{subsec:query}

Segments are sorted by $[\texttt{minKey}, \texttt{maxKey}]$. For a query $[a, b]$:
\begin{enumerate}
    \item Binary search over segments intersecting $[a, b]$ --- $O(\log C)$, $C$ = segment
    count.
    \item Check the first intersecting segment only.
    Suppose the query $[a, b]$
    intersects two segments $S_1 = [\texttt{minKey}_1, \texttt{maxKey}_1]$ and
    $S_2 = [\texttt{minKey}_2, \texttt{maxKey}_2]$ with $\texttt{maxKey}_1 < \texttt{minKey}_2$.
    Then $a \leq \texttt{maxKey}_1$ and $b \geq \texttt{minKey}_2$, so the query covers
    $\texttt{maxKey}_1$ --- a real key.
    The exact-mode sub-filter of $S_1$ reports
    non-empty, and no further segments need to be checked.
    \item Check the fallback filter.
    \item Return ``empty'' only if all agree.
\end{enumerate}

\subsection{FPR Guarantee}\label{subsec:fpr-guarantee}

Every segment sub-filter operates in exact mode (FPR~$= 0$).

\textbf{Individual range.} Consider a range of $m$ sorted keys
$k_0 < k_1 < \dots < k_{m-1}$ from the forward sweep.
The window constraint says any \texttt{minPts} consecutive keys span at most
$\delta$: $k_{i+(\texttt{minPts}-1)} - k_i \leq \delta$ for every valid $i$.
We split the $m-1$ gaps into $\lceil(m-1)/(\texttt{minPts}-1)\rceil$
non-overlapping blocks of $\texttt{minPts}-1$ consecutive gaps; each block
spans $\leq \delta$ by the window constraint, so:
\[
    k_{m-1} - k_0 \;\leq\; \left\lceil \frac{m-1}{\texttt{minPts}-1} \right\rceil \cdot \delta.
\]
With $\delta = \texttt{minPts}\cdot\mathcal{L}/(2\varepsilon)$, the ceiling factor
$\lceil(m-1)/(\texttt{minPts}-1)\rceil$ equals~1 for $m \leq \texttt{minPts}$
(span $\leq \delta < m\mathcal{L}/\varepsilon$, trivially satisfied) and first
reaches~2 at $m = \texttt{minPts}+1$, where the margin is tightest:
\[
    2\delta \;=\; \texttt{minPts} \cdot \frac{\mathcal{L}}{\varepsilon}
    \;<\; (\texttt{minPts}+1) \cdot \frac{\mathcal{L}}{\varepsilon}
    \;=\; m \cdot \frac{\mathcal{L}}{\varepsilon}.
\]
Hence every range from the forward sweep fits the exact-mode budget.

\textbf{Merged segments.} The merge step is conditional: two adjacent ranges are
joined only if the combined span is still below $m'\mathcal{L}/\varepsilon$ for the
combined size $m'$. This preserves the exact-mode invariant by construction.

False positives can therefore come only from the fallback filter, giving overall
FPR~$\leq \varepsilon$.
