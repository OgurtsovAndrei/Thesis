Chapter~\ref{chap:distributions} identified three distribution types.
Sequential and near-sequential keys have small local spread, so exact mode
(Section~\ref{sec:adaptive}) applies directly --- FPR~$= 0$ with no hash needed.
When keys are uniform over a large span, truncation
(Section~\ref{sec:truncation}) is effective: large inter-key gaps mean few phantom
collisions and low FPR.

Clustered keys (OSM, geospatial IDs) fit neither case alone: dense regions inside each
cluster behave like near-sequential data, while the sparse gaps between clusters have
large inter-key distances where truncation works well.

The hybrid idea is to split along this structure --- isolate each dense region into its
own exact-mode sub-filter (FPR~$= 0$), and route the sparse keys between clusters to
a fallback filter.

This chapter describes SegARE, our segmentation algorithm based on 1D DBSCAN.

\section{1D DBSCAN in $O(n)$}
\label{sec:dbscan-1d}

DBSCAN~\citep{ester1996dbscan} is a density-based clustering algorithm.
It takes two parameters: a neighbourhood width~$\delta$ and a density threshold
\texttt{minPts}. A point is a \emph{core point} if it has at least \texttt{minPts}
neighbours within a window of width~$\delta$; a \emph{border point} if it is within
$\delta$ of a core point but not itself dense; and \emph{noise} otherwise. Clusters
grow from core points by absorbing all density-reachable neighbours.

\begin{figure}[h]
  \centering
  \includegraphics[width=0.85\textwidth]{dbscan_1d}
  \caption{1D DBSCAN on a key sequence (minPts~$= 5$). Blue = core points (window
    contains $\geq$ minPts neighbours). Orange = border (within $\delta$ of a core,
    but $<$ minPts in own window). Gray = noise.}
  \label{fig:dbscan-1d}
\end{figure}

In a general metric space, finding the $\delta$-neighbourhood of each point costs $O(n^2)$.
On sorted one-dimensional data the neighbourhood of any key is a contiguous interval, so
a two-pointer sweep suffices: the left pointer advances when the window exceeds~$\delta$,
and the window size is $O(1)$ to check. One forward pass marks the rightmost point of each
dense window; one reverse pass marks the leftmost. Together they identify all core points
in $O(n)$.

\section{SegARE: Design and Algorithm}
\label{sec:hybrid-scan}

\paragraph{Border points are not useful here.}
Standard DBSCAN absorbs border points into the nearest cluster. For range emptiness,
this step adds no value: a border point has fewer than \texttt{minPts} neighbours within
$\delta$, so it lives in a sparse region where the average gap exceeds~$\mathcal{L}/\varepsilon$.
Exact mode does not trigger for such points (Equation~\ref{eq:exact-threshold}), so they
belong in the fallback regardless. SegARE drops border expansion entirely.

\paragraph{Expressing $\delta$ through \texttt{minPts}.}
Standard DBSCAN treats $\delta$ and \texttt{minPts} as independent.
In our setting the exact-mode condition gives us a natural coupling: a core window of
\texttt{minPts} points is exact-mode eligible only if each consecutive pair is spaced at
most $\mathcal{L}/\varepsilon$ apart. The tightest $\delta$ that still admits such a window is:

\begin{equation}
  \delta = \texttt{minPts} \cdot \frac{\mathcal{L}}{\varepsilon}.
  \label{eq:delta}
\end{equation}

This ties $\delta$ to \texttt{minPts}, leaving a single free parameter.

\paragraph{Choosing \texttt{minPts} = 256.}
Each segment stores fixed boundary metadata of roughly 300--500~bits
(\texttt{minKey}, \texttt{maxKey}, and bookkeeping).
For this overhead to be amortized, a segment must hold at least $\sim$256 keys ---
otherwise the per-segment cost exceeds the BPK savings from exact mode.
At the same time, \texttt{minPts} cannot be too large or dense sub-ranges fail to accumulate
enough points to form a cluster.
256 is a practical balance: it filters out micro-clusters whose overhead exceeds their
benefit, while still detecting genuinely dense regions in real distributions.

\subsection{Algorithm}

Dropping border expansion simplifies the implementation: the forward/reverse sweep pair
reduces to a single forward pass.

\begin{enumerate}
  \item \textbf{Forward sweep:} slide a two-pointer window. Whenever the window holds
    $\geq \texttt{minPts}$ keys, record the index range $[\textit{left}, \textit{right}]$.
  \item \textbf{Merge:} adjacent ranges with key-space gap $\leq \delta$ are joined.
  \item \textbf{Fallback:} all keys outside merged ranges go to the fallback filter.
\end{enumerate}

\subsection{Fallback}

Keys not assigned to any segment go to a SODA fallback
(Section~\ref{sec:soda}). SODA is used unconditionally: fallback keys are sparse and
heterogeneous by construction, so truncation cannot provide a reliable FPR guarantee.

\subsection{Query}

Segments are sorted by $[\texttt{minKey}, \texttt{maxKey}]$. For a query $[a, b]$:
\begin{enumerate}
  \item Binary search over segments intersecting $[a, b]$ --- $O(\log C)$, $C$ = segment
    count.
  \item Check each intersecting segment (typically 0--1 in practice).
  \item Check the fallback filter.
  \item Return ``empty'' only if all agree.
\end{enumerate}

\subsection{FPR Guarantee}

Each sub-filter independently targets FPR~$\leq \varepsilon$. By the union bound,
overall FPR~$\leq C\varepsilon$ where $C$ is the number of sub-filters a query touches.
In practice $C = 1$ for most queries, so FPR~$\approx \varepsilon$.
